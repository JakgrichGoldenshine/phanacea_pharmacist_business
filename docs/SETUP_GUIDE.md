## 2. ติดตั้ง Supabase (Database on-cloud)

1. สร้างโปรเจกต์ใหม่ที่ https://supabase.com
2. ไปที่ **SQL Editor** → วางเนื้อหาไฟล์ `database/schema.sql` แล้ว Run
3. วางเนื้อหาไฟล์ `database/seed.sql` แล้ว Run (ข้อมูลตัวอย่างสำหรับทดสอบ)
4. ไปที่ **Project Settings → API** แล้วคัดลอก:
   - `Project URL` → ใช้เป็น `SUPABASE_URL`
   - `service_role` secret key → ใช้เป็น `SUPABASE_SERVICE_ROLE_KEY`

> ⚠️ **ห้ามนำ `service_role` key ไปใช้ฝั่ง frontend เด็ดขาด** — ใช้ในไฟล์
> `backend/.env` เท่านั้น เพราะคีย์นี้สามารถข้าม Row Level Security (RLS) ได้ทั้งหมด

## 5. บัญชีทดสอบ (จาก seed.sql)

ล็อกอินที่หน้าเดียวกัน — `http://localhost:5173/login` — ไม่ว่าจะเป็นลูกค้าหรือพนักงาน
ระบบจะพาไปหน้าที่ถูกต้องให้เองตามอีเมลที่กรอก (ดู 5.1):

| ประเภท   | อีเมล                | รหัสผ่าน     |
|----------|----------------------|--------------|
| ลูกค้า   | somsak@email.com     | Passw0rd!    |
| Admin Console (สิทธิ์เต็ม) | admin@phanacea.local  | Admin123!    |
| พนักงานจัดการคำสั่งซื้อ (สิทธิ์จำกัด) | staff@phanacea.local | Staff123! |
| พนักงาน (อื่นๆ) | somchai@phanacea.local  | Passw0rd!    |

> **ล็อกอิน admin ไม่ได้?** hash ใน `seed.sql` เป็นค่าคงที่ที่ตรวจสอบด้วยตาไม่ได้
> ถ้าไม่ตรงด้วยเหตุใดก็ตาม ให้สร้าง/รีเซ็ตบัญชีใหม่ด้วยคำสั่งนี้แทน — มันเข้ารหัส
> ตอนรัน จึงมั่นใจได้ว่ารหัสที่พิมพ์คือรหัสที่ใช้ได้จริง:
>
> ```bash
> cd backend
> npm run create-admin -- --username admin --email admin@phanacea.local --password 'YourStrongPass123'
> ```
>
> รันซ้ำกับชื่อผู้ใช้เดิม = ตั้งรหัสผ่านใหม่ + เปิดใช้งานบัญชีนั้นอีกครั้ง
> (ใช้เป็นทางกู้คืนเมื่อถูกล็อกออกทั้งหมด) — ถ้าไม่ใส่ `--email` ระบบจะตั้งให้เองเป็น
> `<username>@phanacea.local` ชั่วคราว ควรระบุอีเมลจริงเพื่อใช้ล็อกอินที่ `/login`

## 5.1 Admin Console (back-office)

เข้าถึงได้ที่ `http://localhost:5173/admin` — เป็นระบบแยกต่างหากจากฝั่งลูกค้าโดยสิ้นเชิง
ยกเว้นหน้าล็อกอินซึ่งใช้ฟอร์มเดียวกัน:

- **หน้าล็อกอินเดียวกัน แต่หลังบ้านแยกกันสนิท**: ทั้งลูกค้าและพนักงานกรอกอีเมล/รหัสผ่านที่
  `/login` หน้าเดียว ฟอร์มนี้ยิงไป `POST /api/auth/login` ซึ่งจะค้นอีเมลในตาราง `staff` ก่อน
  ถ้าไม่เจอค่อยไปค้นใน `users` (ดู `backend/src/services/loginService.js`) แล้วตอบกลับว่า
  พบใน role ไหน — ฝั่ง frontend อ่านค่านี้แล้วค่อยตัดสินใจว่าจะพาไป `/admin` หรือ `/`
  ส่วนเซสชันจริงยังคงแยกกันสนิทเหมือนเดิมทุกอย่าง: staff ใช้ตาราง `staff` + `staff_sessions`
  แยกจาก `users` + `user_sessions` ของลูกค้า โทเคนของแอดมินและลูกค้าจึงสลับ/ปนกันไม่ได้
  แม้จะเปิดคนละแท็บพร้อมกัน (เอนด์พอยต์เดิม `POST /api/admin/auth/login` ที่ล็อกอินด้วย
  `username` ยังอยู่และยังใช้งานได้ เผื่อเรียกตรงจากสคริปต์/API ภายนอก แค่ไม่ได้ใช้จาก UI แล้ว)
- **สิทธิ์ตามบทบาท (role)**: มี 4 บทบาท — `owner`, `pharmacist`, `assistant` (เข้าถึงได้ทุกเมนู
  ยกเว้นลบสินค้าซึ่งจำกัดเฉพาะ `owner`) และ **`staff`** (บทบาทใหม่ — เห็นเฉพาะ แดชบอร์ด/POS/
  คำสั่งซื้อ เท่านั้น ไม่เห็นเมนูจัดการสินค้า สต๊อก ใบรับสินค้า หรือข้อความติดต่อ) ผ่าน `requireRole`
  middleware ฝั่ง backend และ role-filtered sidebar ฝั่ง frontend (สองชั้นตรงกัน — ต่อให้พิมพ์ URL
  ตรงๆ หน้าเว็บก็จะเด้งกลับ และ API ก็จะปฏิเสธเช่นกัน)
- หน้าในระบบ: แดชบอร์ด, **จุดขายหน้าร้าน (POS)**, จัดการสินค้า (เพิ่ม/แก้ไข/ปิดการขาย),
  สต๊อกสินค้า (รับเข้า/ปรับปรุง/หมดอายุ/เสียหาย พร้อมประวัติ), **ใบรับสินค้า/Shipments**
  (รับสินค้าจากผู้จัดจำหน่ายเข้าสต๊อก), คำสั่งซื้อทั้งหมด (ดู/แก้ไขสถานะ),
  ข้อความติดต่อจากลูกค้า (ตอบกลับแบบแชท/ปิดคำร้อง)
- **กติกาสำคัญ**: หน้าแก้ไขสินค้าจะแก้ `stock_qty` ไม่ได้โดยตรง (ช่องนี้ถูกล็อกไว้) —
  ต้องปรับผ่านหน้า "สต๊อกสินค้า" หรือ "ใบรับสินค้า" เท่านั้น ซึ่งเรียกฟังก์ชัน `adjust_stock()`
  หรือ `receive_shipment()` ในฐานข้อมูล ที่จะเขียนแถวลง `stock_movements` คู่กันเสมอ
  (audit trail ที่ตรวจสอบย้อนหลังได้ — นี่คือ 3 ทางเดียวเท่านั้นที่แก้ไข `products.stock_qty` ได้:
  checkout ออนไลน์, POS, และรับสินค้าเข้า)

### จุดขายหน้าร้าน (POS) — `/admin/pos`

สำหรับลูกค้าที่มาซื้อและชำระเงินที่หน้าร้านโดยตรง (ไม่ผ่านเว็บ):

- ค้นหาสินค้า → กดเพิ่มลงรายการขาย → เลือกช่องทางชำระเงิน → กด "ยืนยันการชำระเงิน"
- ใส่อีเมลลูกค้า (ไม่บังคับ) เพื่อผูกยอดขายกับบัญชีลูกค้าที่มีอยู่แล้ว ให้ลูกค้าเห็นออเดอร์นี้ใน
  "คำสั่งซื้อของฉัน" ด้วย — ถ้าไม่ใส่หรือหาไม่เจอ ระบบจะขายแบบไม่ผูกบัญชี (ลูกค้าหน้าร้าน)
- **ใช้ฟังก์ชันฐานข้อมูลเดียวกันกับการสั่งซื้อออนไลน์** (`checkout_sale()`) จึงตัดสต๊อกและบันทึก
  `stock_movements` ด้วยกติกาเดียวกันทุกช่องทาง — ต่างกันแค่สถานะเริ่มต้น: POS เป็น `completed`
  ทันที (จ่ายเงินหน้าร้านแล้ว) ส่วนออนไลน์เป็น `pending` (ต้องให้เภสัชกร/พนักงานตรวจสอบและจัดส่งก่อน)

## 5.2 สถานะคำสั่งซื้อ (Order Status)

ทุกคำสั่งซื้อ (ทั้งจากเว็บและจาก POS) มีสถานะที่ปรับได้จากฝั่งแอดมิน และลูกค้าจะเห็นสถานะล่าสุด
ทันทีในหน้า "คำสั่งซื้อของฉัน":

| สถานะ | ความหมาย |
|---|---|
| `pending` | รอดำเนินการ (ค่าเริ่มต้นของออเดอร์ออนไลน์) |
| `preparing` | กำลังจัดเตรียมสินค้า |
| `ready` | พร้อมส่ง/พร้อมให้มารับ |
| `completed` | สำเร็จ (ค่าเริ่มต้นของออเดอร์จาก POS) |
| `cancelled` | ยกเลิก |

แก้ไขได้ที่หน้า "คำสั่งซื้อ" → เลือกออเดอร์ → เลือกสถานะใหม่ → "บันทึกสถานะ"
(เรียก `PATCH /api/admin/sales/:id/status`)

## 5.2b ใบรับสินค้า / Shipments — `/admin/shipments`

ใช้ตาราง `suppliers`, `shipments`, `shipment_items` ที่มีอยู่ในสคีมาแต่ไม่เคยถูกใช้งานจริงมาก่อน:

- เลือกผู้จัดจำหน่าย (หรือเพิ่มใหม่แบบเร็วในหน้าเดียวกัน) → เพิ่มรายการสินค้า (สินค้า/จำนวน/
  ต้นทุนต่อหน่วย/วันหมดอายุ/เลขล็อต) → "บันทึกใบรับสินค้า"
- เรียกฟังก์ชัน `receive_shipment()` ครั้งเดียว ทำทุกอย่างเป็น transaction เดียวกัน: สร้างใบรับสินค้า
  + บันทึกรายการ + เพิ่มสต๊อกสินค้าทุกตัว + บันทึก `stock_movements` (type `restock`,
  ผูก `ref_shipment_id` กลับไปยังใบรับสินค้านั้น) — ถ้าขั้นตอนใดล้มเหลว จะไม่มีอะไรถูกบันทึกเลย
- เมนูนี้ (เหมือนกับจัดการสินค้า/สต๊อก/ข้อความติดต่อ) **ไม่แสดงให้บัญชี role `staff` เห็น**

## 5.3 ศูนย์ช่วยเหลือ / ข้อความติดต่อ (Support) — แชทได้จริง

- **ลูกค้า** (`/support`, ต้องล็อกอิน): ส่งคำร้อง (หัวข้อ + ประเภท + รายละเอียด) แล้วพูดคุยต่อกับ
  ทีมงานได้เหมือนแชท — พิมพ์ข้อความเพิ่มได้เรื่อยๆ ในหน้ารายละเอียดคำร้อง ไม่ใช่ตอบได้ครั้งเดียว
- **แอดมิน** (`/admin/support`): ดูคำร้องทั้งหมด กรองตามสถานะ, ตอบกลับแบบแชทและปรับสถานะ
  (`open` → `in_progress` → `resolved`/`closed`) แยกกัน — ส่งข้อความไม่บังคับให้เปลี่ยนสถานะ
  และการเปลี่ยนสถานะไม่บังคับให้ส่งข้อความ
- ข้อความทั้งหมดเก็บในตาราง `support_ticket_messages` (แยกจาก `support_tickets` ที่เก็บแค่
  หัวข้อ/ข้อความเปิดคำร้อง) และแยกจาก `feedback_records` (ตารางเดิมสำหรับพนักงานบันทึกปัญหา
  คุณภาพสินค้าภายใน) โดยเจตนา — คนละ workflow คนละผู้ใช้งาน จึงไม่ปนกัน
- มี rate limit เฉพาะ (`supportLimiter`: 15 ข้อความ/5 นาที ต่อบัญชี) ป้องกันการส่งสแปมถล่มกล่องข้อความ

## 5.3b การชำระเงิน (Checkout)

ทั้ง 3 ช่องทางเป็น**ระบบสาธิต (demo)** — ยังไม่ได้เชื่อมต่อผู้ให้บริการชำระเงินจริง:

| ช่องทาง | พฤติกรรม |
|---|---|
| เงินสด | แสดงข้อความว่าชำระเมื่อได้รับสินค้า แล้วไปหน้าติดตามสถานะทันที |
| โอนเงิน/QR Code | สร้าง QR Code จริงที่สแกนได้ (ด้วยไลบรารี `qrcode` ฝั่ง frontend ล้วนๆ ไม่ยิง API) ชี้ไปยัง URL ที่กำหนดไว้ใน `Checkout.jsx` (`PAYMENT_QR_URL`) |
| บัตรเครดิต | มีช่องกรอกเลขบัตร/วันหมดอายุ/CVV ให้ครบตามหน้าตาจริง แต่ **ข้อมูลบัตรจะไม่ถูกส่งไป backend หรือบันทึกที่ใดเลย** (ดูคอมเมนต์ใน `Checkout.jsx` → `handleSubmit`) เพราะไม่มีระบบประมวลผลจริงอยู่เบื้องหลัง |

ไม่ว่าจะเลือกช่องทางใด กด "ยืนยันการสั่งซื้อ" แล้วจะไปหน้าติดตามคำสั่งซื้อ (`/orders/:id`) ทันที
พร้อมแถบแจ้ง "สั่งซื้อสำเร็จ" ที่ด้านบน

**หมายเหตุสำคัญ (แก้ไขแล้ว — เคยทำให้สั่งซื้อไม่ผ่านหลังเลือกช่องทางชำระเงิน):**

1. `/checkout` ถูกครอบด้วย `RequireCustomer` แล้ว — เดิมคนที่ยังไม่ล็อกอินกรอกฟอร์ม
   ได้จนจบแล้วค่อยพังตอนกดยืนยัน (API ต้องล็อกอิน) ตอนนี้จะถูกพาไปล็อกอินก่อน
   แล้วพากลับมาที่ `/checkout` ต่อ
2. รายการช่องทางชำระเงินอ่านจาก `GET /api/payment-methods` แล้ว — เดิม hardcode id
   `1/2/3` ไว้ในหน้าเว็บ ถ้า id ในฐานข้อมูลไม่ตรงจะติด foreign key error
3. การเด้งกลับ `/cart` ย้ายไปอยู่ใน `useEffect` — เดิมเรียก `navigate()` ระหว่าง render
   ทำให้หลังสั่งซื้อสำเร็จ (ตะกร้าถูกล้าง) ถูกเด้งกลับตะกร้าแทนที่จะไปหน้าคำสั่งซื้อ
4. ฝั่ง backend หาบัญชีพนักงานสำหรับบันทึก audit trail แบบมี fallback แล้ว
   (`CHECKOUT_STAFF_USERNAME` → `owner` ที่ใช้งานอยู่ → พนักงานคนใดก็ได้)
   เดิมถ้าไม่มีบัญชีชื่อ `admin` พอดี จะสั่งซื้อไม่ได้เลยทั้งระบบ
5. ถ้าฐานข้อมูลมีฟังก์ชัน `checkout_sale` ค้างไว้สองเวอร์ชัน จะขึ้นข้อความบอกให้รัน
   `database/migrations/001_checkout_fix.sql` แทนที่จะขึ้น error ที่อ่านไม่รู้เรื่อง

## 5.3c แชทสดกับทีมงาน (Live Chat) — ใหม่

แยกจากศูนย์ช่วยเหลือแบบคำร้องข้างบนโดยเจตนา: คำร้องคือเคสที่ต้องติดตามจนปิด
ส่วนแชทคือ**บทสนทนาต่อเนื่องเส้นเดียว** ที่ลูกค้าพิมพ์ถามได้ทันทีโดยไม่ต้องกรอกหัวข้อ

- **ลูกค้า** (`/chat`, ต้องล็อกอิน): ห้องแชทเดียวกับร้าน ไม่ต้องสร้างคำร้อง
  ระบบดึงข้อความใหม่ทุก 4 วินาที
- **แอดมิน** (`/admin/chat`): กล่องข้อความสองคอลัมน์ — รายชื่อห้องแชททางซ้าย
  (จุดสีฟ้า = รอตอบ), บทสนทนาทางขวา พร้อมตัวเลขแจ้งเตือนบนเมนู "แชทสด"
- **สิทธิ์**: ทุกตำแหน่งตอบแชทได้ (รวม `staff`) เพราะเป็นงานหน้าร้าน —
  แต่การ "ปิดห้องแชท" จำกัดเฉพาะ `owner`/`pharmacist`/`assistant`
- **เก็บข้อมูลอย่างไร**: ใช้ตาราง `support_tickets` เดิมโดยเพิ่มคอลัมน์ `channel`
  (`'ticket'` / `'chat'`) แทนการสร้างตารางใหม่ — โครงสร้างข้อมูลเหมือนกันทุกอย่าง
  การแยกตารางจะทำให้ต้องเขียน query, สิทธิ์ และหน้าจอซ้ำอีกชุดโดยไม่ได้อะไรเพิ่ม
  ส่วนคอลัมน์ `last_message_at` / `last_sender_type` / `*_last_read_at` คือสถานะ
  ที่ denormalize ไว้ เพื่อให้หน้ารายการห้องแชทเป็น query เดียวจบ
- **ทำไมใช้ polling ไม่ใช่ WebSocket**: ระบบ deploy บน serverless (Vercel) ซึ่งไม่มี
  โปรเซสที่รันค้างไว้ให้ถือ connection — polling ทุก 4 วินาทีจึงเหมาะกว่าและง่ายกว่ามาก
  โดยหยุด poll อัตโนมัติเมื่อผู้ใช้สลับไปแท็บอื่น (ดู `usePolling`)
- **rate limit**: `chatLimiter` 30 ข้อความ/นาที ต่อบัญชี (การอ่านไม่ถูกจำกัดเพิ่ม
  เพราะหน้าจอต้อง poll)

## 5.3d จัดการบัญชีผู้ดูแลระบบ — ใหม่

| หน้า | สิทธิ์ | ทำอะไรได้ |
|---|---|---|
| `/admin/staff` | `owner` เท่านั้น | สร้างบัญชีใหม่, เปลี่ยนตำแหน่ง, เปิด/ปิดใช้งาน, ตั้งรหัสผ่านใหม่ |
| `/admin/account` | ทุกตำแหน่ง | เปลี่ยนรหัสผ่านของตัวเอง (ต้องกรอกรหัสผ่านปัจจุบัน) |

กติกาที่บังคับไว้ฝั่ง server (ไม่ใช่แค่ซ่อนปุ่ม):

- รหัสผ่านต้องยาว ≥ 8 ตัว และมีทั้งตัวอักษรและตัวเลข, เข้ารหัสด้วย bcrypt cost 12
- **ตั้งรหัสผ่านใหม่หรือปิดใช้งานบัญชี = บัญชีนั้นหลุดจากระบบทุกอุปกรณ์ทันที**
  (ล้าง `staff_sessions`) ไม่ต้องรอ JWT หมดอายุ
- ปิดใช้งานบัญชีตัวเอง / เปลี่ยนตำแหน่งตัวเองไม่ได้ และห้ามเหลือบัญชี `owner`
  ที่ใช้งานได้ต่ำกว่า 1 บัญชี — กันไม่ให้ล็อกตัวเองออกจากระบบถาวร

## 7. ความปลอดภัย (Best Practice ที่ใช้ในระบบ)

- **Rate limiting การล็อกอิน**: จำกัด 5 ครั้ง / 15 นาที ต่อ (IP + อีเมล) ป้องกัน brute-force
  — ปรับค่าได้ที่ `LOGIN_RATE_LIMIT_*` ใน `backend/.env`
- **Rate limiting ทั้ง API**: 120 request/นาที ป้องกันการดึงข้อมูลถี่เกินไป
- **Rate limiting ข้อความ/คำร้อง**: 15 ข้อความ/5 นาที ต่อบัญชี (ทั้งฝั่งลูกค้าและแอดมิน)
  ป้องกันสแปมถล่มระบบแชทศูนย์ช่วยเหลือ
- **รหัสผ่าน**: เข้ารหัสด้วย bcrypt (cost 12) ไม่เก็บ plain-text เด็ดขาด
- **Session**: เก็บ session token แบบ hashed (SHA-256) ใน `user_sessions`,
  ตรวจสอบทั้ง JWT และสถานะ `is_valid` ทุกครั้งที่เรียก API ที่ต้องล็อกอิน
- **Staff auth แยกจากลูกค้า**: พนักงาน/แอดมินมีตาราง session ของตัวเอง (`staff_sessions`)
  และ JWT มี `type: 'staff'` กำกับ — โทเคนของลูกค้าจะใช้เรียก API ฝั่งแอดมินไม่ได้และในทางกลับกัน
- **Role-based access**: บาง endpoint (เช่น ลบสินค้า) จำกัดเฉพาะ role `owner` ผ่าน `requireRole` middleware
- **Row Level Security (RLS)**: เปิดใช้ทุกตาราง — ฝั่ง public อ่านได้เฉพาะ
  ข้อมูลอ้างอิง/สินค้าที่ active เท่านั้น ส่วนอื่นเข้าถึงผ่าน backend (service role) เท่านั้น
- **ราคาและสต๊อกคำนวณที่ฝั่งเซิร์ฟเวอร์เสมอ**: ไม่เชื่อค่าจาก client — ทั้งตอนเช็กราคา
  ในตะกร้าและตอน checkout จริง
- **stock_qty ห้ามแก้ตรง**: ทุกการเปลี่ยนแปลงสต๊อกต้องผ่านฟังก์ชัน `checkout_sale()`
  ซึ่งจะบันทึกลง `stock_movements` เพื่อการตรวจสอบย้อนหลัง (audit trail)

## 8. การแจ้งเตือนเมื่อเกิดข้อผิดพลาด

ทุก error จาก backend จะตอบกลับเป็น JSON รูปแบบเดียวกัน:
```json
{ "success": false, "code": "INVALID_CREDENTIALS", "message": "อีเมลหรือรหัสผ่านไม่ถูกต้อง" }
```
Frontend จะแสดงข้อความ `message` เป็นกล่องแจ้งเตือนสีแดงใต้ฟอร์มโดยอัตโนมัติ
(ดูตัวอย่างใน `frontend/src/pages/Login.jsx`)
